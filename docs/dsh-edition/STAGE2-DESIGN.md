# Coucou × DeepSeek Harness — Этап 2: проект интеграции

**Дата:** 2026-11-11  
**Основание:** [STAGE1-RESEARCH.md](STAGE1-RESEARCH.md) (Этап 1).  
**Статус:** проект на согласование. Ничего не реализовано, ничего не изменено.

---

## 1. Принципы

1. **Никакого автоматического разрешения.** Решение `allowed-once` возвращается только после
   явного клика в Coucou и только для конкретного `requestId`.
2. **Fail-closed.** Нет соединения, нет ack, таймаут, отмена, поздний ответ — запрос уходит
   штатному интерфейсу DSH (`next()`), а не разрешается. Если answerer вообще недоступен,
   DSH сам вернёт `unavailable`.
3. **Не обходить approval seam.** Мост — это штатный waterfall-слушатель
   `approval/request`, а не перехват журнала и не подмена политики.
4. **Ничего глобального без действия пользователя.** Переключение модели/усилия — только
   выбранной сессии; `agentDefaultModel.saveSelection()` не вызывается; настройки DSH не
   переписываются, кроме одной строки в `cordis.patch.yml` — с предпросмотром, бэкапом и
   откатом.
5. **Честные данные.** Если DSH не сообщает характеристику — показываем «Неизвестно» или
   «Недоступно», не подставляем глобальные настройки и не выдаём выбранную модель за
   фактическую.
6. **Изоляция от upstream.** Новые модули — отдельные файлы; правки существующих —
   минимальные и перечислены в `docs/UPSTREAM.md`. Форк сохраняет возможность merge из
   upstream.
7. **Никаких секретов.** Мост не читает `.credentials.yaml`, не логирует токены и содержимое
   сообщений; в Coucou не попадают API-ключи DSH.

## 2. Архитектура

### 2.1 Рекомендуемый вариант: «DSH Host Bridge»

```
┌───────────────────────────── DSH desktop (Electron) ─────────────────────────────┐
│  main process ──запускает──► host Node process: dsh --profile desktop            │
│                                   │                                               │
│                                   ├─ sessions / agents / llm / approval          │
│                                   └─ ПЛАГИН @coucou/dsh-bridge (наш, ~800 строк)  │
│                                        │  named pipe, NDJSON, токен               │
└────────────────────────────────────────┼──────────────────────────────────────────┘
                                         │  \\.\pipe\coucou-dsh-<SID>
┌──────────────────────────── Coucou (Tauri 2) ────────────────────────────────────┐
│  Rust: src-tauri/src/dsh/                                                        │
│    client.rs   — подключение, handshake, heartbeat, реконнект                    │
│    protocol.rs — типы сообщений, версия протокола                                │
│    install.rs  — установка/снятие плагина (diff, backup, fingerprint, verify)    │
│    launch.rs   — запуск/остановка/открытие DSH, ожидание готовности              │
│    catalog.rs  — кэш каталога моделей и усилий                                   │
│         │ Tauri events: dsh://state, dsh://event, dsh://approval, dsh://catalog  │
│  WebView: src/island/dsh.ts, src/views/dsh.ts, src/core/dsh.ts                   │
│           существующие State/pill/approval, без переписывания hooks.ts          │
└──────────────────────────────────────────────────────────────────────────────────┘
```

Почему так:

- это **единственный** путь, который видит сессии настольного приложения;
- он даёт аргументы инструментов (через кэш `tool/call` по `callId`), чего нет в
  `approval/request`;
- он использует документированные сервисы Cordis (`agents`, `sessions`, `llm`, `approval`)
  и штатный seam разрешений;
- он не требует CLI `dsh`, второго рантайма и сети;
- он обратим одной строкой патча и папкой плагина.

### 2.2 Альтернативы и почему они не основные

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| **ACP-клиент** (`dsh --profile acp`) | стандарт, `set_config_option`, `request_permission`, `session/list/resume` | не видит настольные сессии; нет CLI на машине; отдельный процесс; нет deep link | второй транспорт, позже |
| **SDK JSON-RPC** | approval + user questions, стабильный протокол | нет закрытия сессии/отмены, отдельный процесс, не настольные сессии | не используем |
| **API gateway (WebSocket)** | полный доступ к живым сессиям | внутренний API, owner-токен, политика доступа, ломкость | не используем |
| **Чтение журнала** (текущий мост) | ничего не ставит в DSH, уже работает | только наблюдение, задержка, нет разрешений | fallback-режим, выключить по умолчанию |
| **Плагин в хосте** | всё нужное, live, аргументы, переключение | правка профиля DSH, зависит от внутренних API | **основной** |

### 2.3 Границы ответственности

- Плагин **не** создаёт сессии, **не** отправляет prompt'ы, **не** меняет политику
  разрешений и sandbox, **не** завершает DSH. Он наблюдает и отвечает на разрешения.
- Coucou **не** пишет в журнал сессий DSH, **не** читает credentials, **не** меняет
  `settings.json` DSH.
- Всё, что показывается в острове, приходит одним каналом; текст терминала не парсится.

### 2.4 Что DSH поддерживает штатно, а что требует нашей интеграции

**Штатно, без нашего кода:**

- политика разрешений `ask` / `never`, детерминированный отказ при `never`;
- одноразовые исходы `allowed-once` / `rejected` / `cancelled` / `unavailable`;
- sandbox-пресеты (`read-only` / `workspace-write` / `danger-full-access`) и их смена
  командой `/permission`;
- выбор модели и усилия для сессии (`agent.model.select`, ACP
  `session/set_config_option`), применение со следующего шага;
- каталог моделей/усилий (`ctx.llm.listProviders/listModels`);
- события сессии и журнал (`session/event`, `session.v4.jsonl.zstd`);
- запуск и фокус окна (`dsh://open`).

**Требует дополнительной интеграции (наш плагин + Coucou):**

- доставка `approval/request` в остров и возврат клика в ту же сессию;
- показ аргументов/файлов запроса (join `approval/asked` ↔ `tool/call` по `callId`);
- live-состояние и активность **настольных** сессий в острове;
- переключение модели/усилия **из острова** для выбранной сессии;
- запуск/остановка DSH и открытие его окна из Coucou;
- защита от установки оригинального Coucou поверх модифицированного.

**Не поддерживается в DSH 0.2.2-rc.1 в принципе:**

- «Allow always» / запоминание правил / отзыв грантов;
- deep link на конкретную сессию (только `dsh://open`);
- сведения о фактической модели на стороне провайдера (маршрут не раскрывается);
- подключение стороннего клиента к живым настольным сессиям по документированному API
  (только плагин внутри хоста).

## 3. Компоненты

### 3.1 Плагин `@coucou/dsh-bridge` (JS ESM, без сборки)

Живёт в `%LOCALAPPDATA%\Coucou\dsh-plugin\` (файл `bridge-<version>.mjs` + `protocol.mjs`).
Загружается строкой в `cordis.patch.yml`:

```yaml
- insert:
    - id: coucou-dsh-bridge
      name: 'file:///C:/Users/<user>/AppData/Local/Coucou/dsh-plugin/bridge-1.mjs'
      config:
        protocol: 1
        descriptor: 'C:/Users/<user>/AppData/Local/Coucou/dsh/runtime.json'
```

(точный синтаксис `name` проверить прототипом; запасной вариант — относительный путь
`./coucou-bridge/bridge.mjs` внутри профиля).

Модули плагина:

| Файл | Роль |
|---|---|
| `bridge.mjs` | вход Cordis-плагина: подписки, жизненный цикл, pipe-сервер |
| `approval.mjs` | answerer `approval/request`: ack, ожидание, таймаут, `next()` |
| `sessions.mjs` | `ctx.agents`/`session/event` → состояние сессий и шаги |
| `catalog.mjs` | `ctx.llm` → каталог провайдеров/моделей/усилий, обновления |
| `protocol.mjs` | типы сообщений, версия, валидация |
| `wire.mjs` | NDJSON-кадрирование, лимиты, heartbeat |

Ключевые подписки:

```js
ctx.on('approval/request', onApproval)          // waterfall, ответ = исход
ctx.on('session/event', onSessionEvent)         // turn/step/tool/model/approval
ctx.on('agent/status', onAgentStatus)
ctx.on('llm/models-updated', refreshCatalog)
ctx.on('llm/adapters-updated', refreshCatalog)
```

`onApproval(req, next)`:

1. Если нет подключённого клиента Coucou или интеграция выключена → `return next()`.
2. Взять из кэша `tool/call` по `req.callId` аргументы, файлы, заголовок.
3. Отправить `approval.asked`; ждать `approval.ack` не дольше **1500 мс**.
4. Нет ack → `return next()` (штатная карточка DSH).
5. Есть ack → ждать `approval.answer` не дольше **110 с**, гонка с `req.signal`.
6. `allow` → `allowed-once`; `deny` → `rejected`; отмена/таймаут/разрыв → `next()`.
7. Поздний ответ после `next()` игнорировать (request уже не наш).

Ни при каких условиях плагин не возвращает `allowed-once` без `approval.answer`.

## 4. Протокол моста

### 4.1 Транспорт

- Windows named pipe `\\.\pipe\coucou-dsh-<SID>`; имя и токен — в
  `%LOCALAPPDATA%\Coucou\dsh\runtime.json` (каталог уже приватный для пользователя).
- Кадрирование: **NDJSON**, один JSON-объект на строку, UTF-8, максимум 1 МиБ на строку.
- Первое сообщение клиента — `hello` с токеном; плагин отвечает `ready` или закрывает канал.
- Heartbeat: `ping` от плагина каждые 5 с; 3 пропущенных → разрыв, реконнект с backoff
  (250 мс → 5 с), состояние `connection lost`.
- Один клиент (Coucou). Второй клиент отклоняется.

### 4.2 Сообщения плагин → Coucou

| `t` | Поля | Когда |
|---|---|---|
| `ready` | `protocol`, `dshVersion?`, `hostPid`, `catalog`, `sessions[]` | после `hello` |
| `catalog` | `providers[]`, `fetchedAt` | при изменении каталога |
| `session.upsert` | `sessionId`, `title?`, `cwd`, `agentPreset?`, `createdAt` | новая/изменённая сессия |
| `session.state` | `sessionId`, `state`, `since`, `turn?`, `step?` | смена состояния |
| `session.model` | `sessionId`, `provider`, `providerName?`, `model`, `modelName?`, `reasoningEffort?`, `source`, `pending` | выбор/подтверждение |
| `session.step` | `sessionId`, `ts`, `kind`, `tool?`, `title`, `target?`, `files?` | шаг/инструмент |
| `session.turn` | `sessionId`, `phase` (`start`/`end`), `ts`, `reason?`, `finalText?`, `durationMs?` | начало/конец хода |
| `approval.asked` | `requestId`, `sessionId`, `callId?`, `tool`, `reason`, `title?`, `command?`, `files?`, `expiresAt` | запрос решения |
| `approval.resolved` | `requestId`, `outcome` (`allowed-once`/`rejected`/`cancelled`/`unavailable`/`native`/`expired`) | запрос закрыт |
| `log` | `level`, `message`, `ts` | диагностика |

### 4.3 Сообщения Coucou → плагин

| `t` | Поля | Смысл |
|---|---|---|
| `hello` | `protocol`, `token`, `client`, `pid` | аутентификация |
| `approval.ack` | `requestId` | карточка на экране, можно ждать |
| `approval.answer` | `requestId`, `decision` (`allow`/`deny`) | клик пользователя |
| `approval.decline` | `requestId` | «ответить в DSH» → `next()` |
| `session.setConfig` | `requestId`, `sessionId`, `configId` (`model`/`reasoning_effort`), `value` | смена настройки сессии |
| `sessions.list` | `requestId` | снимок сессий |
| `catalog.get` | `requestId` | снимок каталога |
| `ping` / `pong` | `ts` | heartbeat |

Ответы на команды: `result` с тем же `requestId` (`ok`, `value?`, `error?{code,message}`).

### 4.4 Ошибки

Коды: `protocol`, `unauthorized`, `unknown_request`, `unknown_session`,
`unsupported_config`, `invalid_value`, `stale_request`, `internal`.  
Ошибка смены настройки возвращается в UI, текущее значение не подменяется.

### 4.5 Приватность

- В Coucou уходят только метаданные и короткие тексты: имя инструмента, команда/путь,
  первые 200 символов причины, имя сессии (усечённое), `cwd` (в компактном режиме — только
  имя папки).
- Содержимое файлов, ответы модели, системные промпты, аргументы целиком — не уходят.
  Диффы — только `path` + `+N/−M`; полный diff не передаётся.
- Логи плагина и Coucou не содержат текстов запросов, ключей и путей к credentials.
- Буфер обмена и журнал диагностики очищаются от токена канала.

### 4.6 Режимы работы

| Режим | Условие | Поведение |
|---|---|---|
| `plugin` | плагин установлен, DSH работает, канал есть | полная интеграция |
| `plugin-stopped` | плагин установлен, DSH не запущен | пилюля «DSH остановлен», кнопка запуска |
| `not-installed` | плагина нет | страница настроек предлагает установить; DSH-пилюли нет |
| `legacy-bridge` | старый мост включён, плагин выключен | только наблюдение (как сейчас), без разрешений |
| `lost` | был `ready`, канал разорван | карточки сняты, «соединение потеряно», реконнект |

При включении плагина Coucou обнаруживает старый мост (папка + автозапуск) и предлагает
выключить его с бэкапом; молча не удаляет.

## 5. Состояния

### 5.1 DSH в целом

| Состояние | Условие |
|---|---|
| `stopped` | процесс не найден, канала нет |
| `starting` | процесс запущен Coucou, `ready` ещё не получен (таймаут 60 с) |
| `ready` | handshake выполнен, нет открытых ходов |
| `working` | есть хотя бы один открытый ход |
| `waiting` | есть хотя бы один неотвеченный `approval.asked` |
| `finished` | последний ход завершён (5 с, затем `ready`) |
| `error` | ошибка запуска/протокола/последнего хода |
| `lost` | был `ready`, канал разорван; карточки сняты |

### 5.2 Сессия

`idle` → `thinking` (turn/start, нет tool) → `working` (tool/call) → `waiting`
(approval) → `finished` (turn/end) → `idle`; `error` при `turn/end` с ошибкой;
`unknown` если событий нет.

Несколько сессий: пилюля одна (`agent_deepseek-harness`), активная сессия выбирается
в расширенной карточке; компактный режим показывает активную. Карточка разрешения всегда
привязана к своей сессии и показывает её имя.

## 6. Разрешения

### 6.1 Последовательность

```
DSH tool wants approval
  └─ approval/request (waterfall)
       └─ plugin: client connected?
            no  → next()  → штатная карточка DSH
            yes → approval.asked → Coucou
                     │
                     ├─ ack ≤1.5s? ── no → next() → DSH UI
                     │                yes
                     ↓
              карточка в острове (Allow once / Deny / Open DSH)
                     │
        Allow once ──┼──→ approval.answer → allowed-once
        Deny ────────┼──→ approval.answer → rejected
        Open DSH ────┼──→ approval.decline → next() → DSH UI
        таймаут 110с ─┴──→ next() → DSH UI, карточка снята
```

### 6.2 Что показываем

- тип операции: инструмент (`pwsh`, `edit`, `write`, `web_fetch`…) и `toolName`;
- причина из `approval/request.reason` (например, «escalate sandbox to danger-full-access: …»);
- команда/инструмент: `command` или `title` из кэша `tool/call`;
- аргументы: `command`, `file_path`, `path`, `query` и т. п.;
- затрагиваемые файлы: `files` (из аргументов и/или `locations`, если появятся);
- сессия и проект (`cwd` в одну строку);
- таймер до истечения.

Если аргументов нет (запрос пришёл без `callId` или кэш пуст) — честно показываем только
инструмент и причину, без выдуманных деталей.

### 6.3 Кнопки

- **Allow once** — `allowed-once`.
- **Deny** — `rejected`.
- **Open DSH** — `next()`, ответ в штатном интерфейсе.
- **Allow always — не показывается**: DSH не поддерживает такой политики. В подсказке можно
  объяснить, что «навсегда» в DSH нет, есть только политика сессии `ask/never` и пресеты
  sandbox, которые меняются отдельно и осознанно.

**Следствие, которое надо явно сказать в UI:** пока интеграция включена и Coucou успел
подтвердить показ, штатная карточка DSH не появляется — решение принимается в острове.
Кнопка **Open DSH** (и выключение интеграции) возвращают штатное поведение.

### 6.4 Крайние случаи

| Случай | Поведение |
|---|---|
| Нет ответа | `next()`; ничего не разрешено |
| Разрыв канала | все pending → `next()`; карточки сняты; состояние `lost` |
| Отмена инструмента/хода | `approval.resolved cancelled`; карточка снята; поздний клик игнорируется |
| Дубликат запроса | повторный `asked` не создаёт вторую карточку; повторный ack |
| Больше 5 запросов | очередь, как в Coucou; новый сверх лимита → `next()` |
| Пришло после `Stop`/`SessionEnd` | карточка снимается, ответ не отправляется |
| DSH перезапустился | старые `requestId` недействительны; полный сброс состояния |
| Политика `never` | DSH отклоняет до плагина; плагин ничего не получает |

## 7. Позиционирование острова

### 7.1 Модель настроек

Добавить в `Settings` (Rust и TS зеркально):

```rust
pub struct IslandPlacement {
    pub mode: String,        // "bottomLeft" (default) | "bottomRight" | "custom" | "topCenter"
    pub offset_x: f64,       // логические px от края рабочей области
    pub offset_y: f64,
    pub custom_x: f64,       // логические px от левого/верхнего края рабочей области
    pub custom_y: f64,
}
```

Поле `screen` остаётся выбором монитора (`primary`/`cursor`/`at:…`); `mode` его не дублирует.
Новые поля с `Default`, старый `settings.json` читается без миграции.

### 7.2 Геометрия

Пусть `W=720`, `H=320` — панель; `cw,ch` — свёрнутый размер; `wa` — work area монитора
(физическая, конвертируется в логические через `scale_factor`).

| Режим | Позиция окна (логические) | Рост |
|---|---|---|
| `bottomLeft` | `x = wa.left + offset_x`, `y = wa.bottom - offset_y - h` | вверх и вправо |
| `bottomRight` | `x = wa.right - offset_x - w`, `y = wa.bottom - offset_y - h` | вверх и влево |
| `custom` | `x = wa.left + custom_x`, `y = wa.top + custom_y`, клампить в `wa` | вправо и вниз |
| `topCenter` | текущее поведение (совместимость) | вниз |

Для свёрнутого состояния `w=cw, h=ch` и та же привязка (низ/верх), чтобы остров «рос»
из своего угла. Клампить итоговый прямоугольник в `wa` с учётом панели задач.

### 7.3 Перетаскивание

- Ручка — шапка острова (не Mochi, чтобы не конфликтовать с «потаскать Mochi»).
- `pointerdown` → `window.start_dragging()`; по `onMoved` (debounce 200 мс) читаем
  `outerPosition`, определяем монитор по центру окна, пересчитываем логические координаты.
- Если окно близко к нижнему краю (≤ 32 px) — прилипание к `bottomLeft`/`bottomRight`
  по половине экрана; иначе `custom` с сохранением `custom_x/custom_y`.
- Сохранение в `settings.json` при отпускании; при следующем запуске — восстановление;
  если монитор исчез — fallback на primary + `bottomLeft`.

### 7.4 Мультимонитор и DPI

- Все сохранённые координаты — логические, относительно рабочей области конкретного монитора
  (ключ монитора — существующий `DisplayId`, `at:<x>,<y>|name|WxH`).
- При смене масштаба/разрешения — пересчёт и клампинг; при отключении монитора — primary.
- Перетаскивание между мониторами с разным DPI: координаты берём из физического
  `outerPosition`, делим на `scale_factor` целевого монитора.

### 7.5 Что не трогаем

Анимации, прозрачность, клик-сквозность, компакт/расширенный режим, `PollGate`, звуки.
Меняются только `apply_geometry`, точка привязки контента (CSS-класс на `body`) и
`transform-origin` анимаций.

## 8. Модель и усилие: данные и отображение

### 8.1 Источники

| Поле | Источник | Если нет |
|---|---|---|
| провайдер (маршрут) | `agent.model.current().provider` | «Неизвестно» |
| имя провайдера | запись провайдера в каталоге, если есть `name` | id маршрута |
| модель (id) | `…model` | «Неизвестно» |
| имя модели | каталог `listModels` по id | id |
| усилие | `…reasoningEffort` | «По умолчанию» / «Неизвестно» |
| факт. модель провайдера | — | «Провайдер не сообщает» |
| сессия | `session.id`, `session/title` | короткий id |
| состояние | события хода | «Неизвестно» |

### 8.2 Компактный режим

Чип в компактном острове (рядом с точками пилюль), только когда активна DSH-пилюля:

```
V4.1 Flash · HIGH · Working
```

- имя — `name` из каталога, обрезается CSS (`max-width`, ellipsis), без хардкода;
- усилие — id в верхнем регистре (`OFF/LOW/HIGH/MAX`), если DSH его сообщает;
- состояние — `Working/Waiting/Done/Error` (локализуется);
- если данных нет: `DSH · — · Working` и подсказка «модель не сообщается».

### 8.3 Расширенный режим

Карточка DSH:

- шапка: имя сессии, проект (`cwd`), состояние, таймер хода;
- блок модели: провайдер, полный id, отображаемое имя, усилие, «применено/выбрано»;
- переключатели: модель (группы по провайдеру) и усилие (только поддерживаемые);
- строка «Фактическая модель: не сообщается провайдером»;
- список активных сессий с их моделью/усилием (переключение активной);
- последние события (шаги);
- кнопки: Open DSH, обновить каталог, «ответить в DSH» для зависшего запроса.

### 8.4 Разные сессии

Состояние сессий хранится в `DshSession[]` в Rust и зеркалится в TS; активная сессия —
`State.dsh.activeSessionId`. Карточка разрешения всегда показывает сессию запроса,
даже если активна другая. Переключение модели/усилия действует на выбранную сессию.

## 9. Переключение модели и усилия

### 9.1 Команда

`session.setConfig { sessionId, configId, value }`

Плагин:

1. находит живой агент по `sessionId` (`ctx.agents.get`);
2. для `model`: проверяет, что `value` есть в текущем каталоге; разбирает
   `provider/model`; вызывает `agent.model.select({provider, model})`;
3. для `reasoning_effort`: берёт `resolveModelInfo(provider, model)`, проверяет, что
   `value` есть в `reasoning.efforts` (или `""` = default); вызывает
   `agent.model.select({provider, model, reasoningEffort})`;
4. возвращает `result` с новым `current()` и `pending: true`.

### 9.2 Подтверждение

- `select()` пишет `model/selection` в журнал; плагин видит событие и шлёт `session.model`
  с `pending: false` только после того, как следующий `request/header` (или `step/start`)
  подтвердил новый выбор.
- До этого UI показывает: «Выбрано: X. Применится к следующему шагу» — как требует ТЗ.
- Ошибка (`unknown model`, `unsupported effort`, DSH недоступен) → `result.error`,
  UI возвращает прежнее значение и показывает причину.

### 9.3 Ограничения

- Нельзя менять модель/усилие, если сессия не жива (только что закрылась) — ошибка
  `unknown_session`.
- Нельзя предлагать усилие, которого нет у модели, — список строится из каталога.
- Нельзя менять глобальные настройки — `agentDefaultModel` не трогаем.
- Нельзя менять настройку «за пользователя» — только по клику.

## 10. Настройки и установка плагина

### 10.1 Страница «DeepSeek Harness»

Секции:

1. **Интеграция**: вкл/выкл; статус (не установлен / установлен / работает / ошибка);
   версия плагина и протокола; кнопка «Проверить».
2. **DSH**: путь к exe (автоопределение + «Обзор…»), «Проверить», версия, статус.
3. **Запуск**: «Запускать DSH вместе с Coucou», «Запускать Coucou при входе в Windows»
   (существующая настройка), «Открывать DSH при клике на пилюлю».
4. **Плагин**: «Установить…», «Переустановить…», «Удалить…» — каждый с предпросмотром
   точного diff, путём бэкапа и подтверждением.
5. **Диагностика**: уровень лога, «Открыть журнал», «Скопировать диагностику»,
   последние 50 строк, кнопка «Сбросить соединение».

### 10.2 Установка плагина (безопасно)

1. Прочитать `%USERPROFILE%\.dsh\profiles\desktop\cordis.patch.yml` (или `[]`).
2. Проверить, что файл — YAML-массив; иначе отказать, ничего не писать.
3. Сформировать новый текст: добавить (или заменить) один `insert`-блок
   `id: coucou-dsh-bridge`; остальное — байт-в-байт.
4. Показать diff, путь файла, путь бэкапа, SHA-256 исходника (fingerprint).
5. По клику: проверить fingerprint, сохранить
   `cordis.patch.yml.<timestamp>.bak`, записать атомарно (temp + rename), перечитать и
   проверить, что наш блок ровно один.
6. Написать `install-state.json` (версия, путь, хэш, дата) в `%LOCALAPPDATA%\Coucou\dsh\`.
7. Сказать «DSH может применить патч без перезапуска; если нет — перезапустите DSH».
8. Удаление — обратная операция: убрать только наш блок, бэкап, проверка.

Никогда не трогаем: `package.json` профиля, `.credentials.yaml`, `settings.json` DSH,
другие строки патча.

### 10.3 Запуск/остановка

- «Запустить DSH»: `spawn(exe)`, запомнить pid, ждать `ready` ≤60 с; ошибка → состояние
  `error` с текстом.
- «Открыть DSH»: если процесс есть — `dsh://open` через ShellExecute; иначе запустить.
- «Остановить»: только для процесса, запущенного Coucou (owned pid). Вежливое закрытие
  главного окна (WM_CLOSE) → ожидание 10 с → предложение завершить процесс.
  Для чужого процесса кнопка disabled с объяснением.
- «Перезапустить»: stop (owned) + start; иначе — «закройте DSH вручную».

### 10.4 Безопасность установщика

- Плагин пишется только в `%LOCALAPPDATA%\Coucou\dsh-plugin\` (каталог пользователя).
- Патч DSH — единственный изменяемый файл; перед записью — бэкап и fingerprint, после —
  повторное чтение и проверка «ровно один наш блок».
- Никаких `package.json`, lock-файлов, credentials, `settings.json` DSH.
- Токен канала — 128 бит, файл в приватном каталоге, в логи не попадает.
- Команды принимаются только от процесса того же пользователя (проверка токена + PID).
- В плагине нет сетевых вызовов; он не читает файлы, кроме собственного descriptor.

## 11. Обновления и синхронизация с upstream

### 11.1 Обновления приложения

- Заменить `RELEASES_URL`/`RELEASES_PAGE` на форк (или отключить автоустановку).
- Свои теги: `dsh-vX.Y.Z`; имена ассетов с маркером `Coucou-DSH-…`.
- Жёсткое правило: устанавливать только релиз, у которого тег начинается с `dsh-v` и в
  ассетах есть наш маркер; иначе «Обновление недоступно — это не сборка Coucou DSH Edition».
- Проверка SHA-256 обязательна; без digest — не устанавливать.
- Upstream-релизы можно **показывать** как «доступна версия оригинала» для анализа, но не
  устанавливать.
- Лицензия: публичные релизы форка — только после переименования/замены ассетов; для личного
  использования имя можно оставить. Это фиксируется в `docs/DISTRIBUTION.md`.

### 11.2 Git и upstream

- `origin` — форк, `upstream` — `Louis-CFM/coucou`.
- Рабочая ветка `dsh/0.5.9` (не `main`); `main` форка — зеркало upstream.
- Собственные изменения — новые файлы + минимальные правки; список правок в
  `docs/UPSTREAM.md` (файл, причина, как разрешать конфликты).
- Синхронизация: `git fetch upstream`, ветка `sync/upstream-YYYY-MM-DD`, merge/rebase,
  прогон тестов, отчёт. Автоматическое слияние в рабочую ветку — только с согласия
  пользователя.
- Форк **самодостаточен**: сборка не обращается к upstream; upstream нужен только для
  синхронизации. `package-lock.json`/`Cargo.lock` фиксируют зависимости.
- CI: GitHub Actions — frontend-тесты, `cargo test`, `cargo check` (без сборки установщика).

### 11.3 Поручения DSH (архитектура обновлений из ТЗ)

В `docs/UPSTREAM.md` описать готовые промпты/чек-листы для DSH:

1. проверка новых тегов/релизов;
2. diff upstream → наш форк;
3. классификация изменений (нужно/не нужно/конфликт);
4. перенос в ветку `sync/...`;
5. регрессионные тесты;
6. отчёт с рисками.

Никаких автоматических merge/установок без подтверждения.

### 13.4 Интеграционные (ручные, сценарий)

1. Запуск Coucou без DSH → «остановлен», без ошибок.
2. Запуск DSH из Coucou → `starting` → `ready`.
3. Сессия DSH: prompt → `working` → шаги → `finished`.
4. Разрешение: карточка, Allow once → инструмент выполняется; Deny → отказ.
5. Allow без клика невозможен: закрыть Coucou при висящей карточке → DSH показывает свою.
6. Разрыв: убить хост DSH → `lost`, карточки сняты, повторный запуск → реконнект.
7. Модель: смена в острове → «применится к следующему шагу» → подтверждение.
8. Разные сессии: у каждой своя модель/усилие; переключение не влияет на другую.
9. Новая модель/усилие появляются из каталога без пересборки.
10. Позиция: bottomLeft → перезапуск → сохранилась; перетаскивание; второй монитор; 125/150 %.
11. Регрессии: Claude Code/Codex/Copilot карточки, чат, интеграции, трей.

- сборка Rust (`cargo build`), frontend (`npm run build`), запуск приложения;
- остров, позиция, сохранение;
- подключение DSH, события, разрешение, Allow/Deny, потеря связи;
- отсутствие авто-разрешения (тест + ручная проверка);
- модель/усилие, разные сессии, переключение, изменение во время задачи;
- отсутствие регрессий.
