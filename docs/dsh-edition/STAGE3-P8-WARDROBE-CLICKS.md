# Приоритет 8: одежда на большой Моте и клики в правой части экрана

**Дата:** 2026-11-13  
**Точка отката:** `3ae97d13244d92e81754f3b3d45596e3b4bc8213`

## 1. Шапка пропадает: причина найдена в коде, но НЕ подтверждена воспроизведением

`island.ts` — `chooseOutfit` и `previewOutfit` меняют состояние и вызывают
`State.notify()`, но **не запускают цикл кадров**. Одежда анимируется
(`setOutfit` заводит твин `outfitPresence`), а без кадров твин не шагает и на
холст ничего не попадает.

Отсюда ровно тот симптом, который вы описали: «эффект появляется только после
переключения Моти на другого» — переключение пилюли меняет геометрию, а
`applyGeometry` вызывает `ensureRunning()`, и только тогда цикл просыпается и
доигрывает накопленную анимацию.

**Исправление:** оба обработчика теперь вызывают `ensureRunning()` перед
`State.notify()`.

```ts
chooseOutfit: (selection) => {
  ...
  this.engine.triggerEmote("proud");
  this.ensureRunning();   // ← добавлено
  State.notify();
},
previewOutfit: (outfit) => {
  State.wardrobePreview = outfit;
  this.ensureRunning();   // ← добавлено
  State.notify();
},
```

**Честно о статусе:** причина в коде видна, но **воспроизвести дефект я не смог** —
за всё время проверки шапка отображалась корректно во всех пяти состояниях.
Возможно, моя сборка ведёт себя иначе из-за таймингов, а может быть, цикл
просыпался по другой причине. Исправление устраняет доказанную дыру (изменение
состояния без кадров), но **не проверено на вашем сценарии**.

## 2. Клики в правой части экрана

Нашёл ту же семью ошибок, что и с гардеробом: `applyGeometry` сообщал
прямоугольник панели, посчитанный как «по центру окна»:

```ts
const originX = this.placeFromBottom ? 0 : (viewportW - w) / 2;   // было
```

Для всех нижних привязок это давало левый край, а для правых — заведомо неверную
точку. Прямоугольник уходит в Rust и строит из себя область попадания мыши
(`refresh_click_through`, проверка `on_island` в опросе курсора).

**Исправление:** прямоугольник следует за фактической привязкой панели, и
считается он теми же переменными, что и инлайновое позиционирование, — чтобы
два места не могли разойтись снова:

```ts
const centred = mode === "topCenter";
const right = RIGHT_MODES.includes(mode);
const originX = centred ? (viewportW - w) / 2 : right ? Math.max(0, viewportW - w) : 0;
```

### Оговорка, которую надо проверить

Честно: на Windows окно всегда **равно** панели по размеру (`apply_geometry`
задаёт `pw`/`ph` из тех же `lw`/`lh`), поэтому `viewportW - w == 0` и правка
даёт ноль. Область попадания на Windows вообще не применяется:
`platform::set_input_region` — пустая заглушка, работает опрос курсора.

Значит **эта правка сама по себе не объясняет** непроходящие клики справа.
Остаются два кандидата, и я их не развёл:

1. **Экран был заблокирован** во время вашей проверки — тогда клики не доходят
   никуда, и «не реагирует справа» было бы совпадением с тем, где стоял курсор.
2. **Что-то в проверке `on_island`** при правой привязке. Код читает
   `gate.rect` под мьютексом в цикле опроса; если прямоугольник устаревает
   между кадрами, край области может не совпасть с панелью.

Мои собственные проверки кликов прошли (остров свернулся с `720x320` до
`132x24`), но происходило это в том числе по таймеру автозакрытия (15 с), так
что за доказательство я это не выдаю.
