# P15 — почему запросы не приходят, и почему больше не «слетит»

Дата: 14.11.2026. Сборка: Coucou 0.5.9 DSH Edition, мост build 13.
Проверено на живой установке (`%LOCALAPPDATA%\Coucou`), DSH 0.2.2-rc.3.

## Что просил пользователь

> не приходят запросы одобрения, почини так, чтобы не слетало при обновлении DSH

Речь о двух вещах: (1) запросы не доходят до острова, (2) после обновления DSH перехват
отключается и остаётся выключенным.

## Четыре независимые причины, каждая давала тот же симптом

### 1. Версия DSH решала, жить ли перехвату

В `bridge.mjs` стоял `SUPPORTED_DSH = ['0.2.2-rc.1']`. DSH обновился до `0.2.2-rc.3`,
проверка не прошла — и плагин **сам** выключил перехват:

```
warn compat: DSH 0.2.2-rc.3 is not supported (expected 0.2.2-rc.1)
warn approvals: disabled (incompatible DSH); DSH keeps its own prompts
```

Тег версии — не тот API, который вызывает плагин. Теперь версия читается, пишется в лог
и сообщается Coucou, но **ничего не выключает**. Требования к хосту: уметь слушать события
(`ctx.on`). Отсутствие службы `approval` или каталога моделей — заметка в логе, не отказ.

Следствие: обновление DSH, сохранившее API, больше не трогает перехват вообще.

```
info compat: DSH 0.2.2-rc.3; the version is a label, not a gate
```

### 2. Остров стоял позади чужих ответчиков

`approval/request` — waterfall: цепочка останавливается на первом слушателе, который не
вызвал `next()`. Мост регистрировался обычным `ctx.on`, то есть **последним**. На этой
машине впереди него уже было двое, а после перезапуска — трое и четверо:

```
info approvals: enabled; the island answers first (4 other answerer(s) were already registered)
```

Среди них — собственная браузерная карточка DSH (`dsh-client-ui-approval`) и
`api-remotes`. Значит запрос уходил в окно DSH, а остров его не видел никогда. Теперь мост
регистрируется с `{ prepend: true }` и стоит первым независимо от порядка загрузки.

Правило безопасности сохранено: `prepend` — не вето. Нет клиента, нет подтверждения
карточки, отказ или таймаут — вызывается `next()`, и DSH показывает своё окно.

### 3. Один старый токен убивал мост до перезапуска DSH

`runtime.json` перезаписывается при каждом старте плагина. Если Coucou держал в руках
прежний токен (обычное дело сразу после обновления моста), происходило:

```
warn  pipe: rejected a client (protocol or token mismatch)
error pipe: host exited (code 5)
```

`kick` не только отключал клиента, но и останавливал IO-воркер, а тот закрывал дескриптор
под работающим циклом. Хост выходил с кодом 5 и **больше не поднимался**: плагин загружен,
канала нет, все запросы молча уходят в окно DSH. Это и есть «слетело после обновления».

Исправлено на трёх уровнях:

- `kick` только отключает клиента — канал продолжает слушать;
- любой сбой ввода-вывода считается уходом клиента, а не смертью моста (код 5 больше не
  появляется);
- если хост умер по-настоящему, супервизор поднимает его с задержкой (1 с → 30 с), а
  `stop()` снимает автоперезапуск.

### 4. DSH держал в памяти старый модуль

DSH кэширует импортированный модуль по адресу. Запись нового файла на диск ничего не
меняла: плагин продолжал работать старым кодом — со старым представлением о версиях.
Параметр `?rev=` в URL не помог (проверено: журнал показывал прежний build). Понадобилось
три вещи:

- файл называется по отпечатку исходника: `bridge-<rev>.mjs`;
- `refresh()` при старте Coucou выгружает и снова загружает запись профиля
  (`enabled: false` → живая запись) — DSH применяет изменения из патча через свой watcher,
  и окно стабилизации ~2 с требует паузы 3 с между записями;
- **мост обновляет себя сам**: работает наблюдатель за своей папкой, новый файл сначала
  импортируется и проверяется, и только потом старый экземпляр останавливается.

Проверено живьём:

```
info reload: bridge-03e4c946.mjs is newer than bridge-2767cb84.mjs; handing over
info bridge start (protocol=1 build=12)
info pipe: host ready
info pipe: Coucou connected
```

## Что ещё исправлено попутно

- **Каталог.** Установщик писал модули в `%APPDATA%\Coucou` (настройки), а клиент читает
  токен из `%LOCALAPPDATA%\Coucou` (данные). Мост подключался «в никуда». Теперь оба пути
  совпадают с `wire::state_dir()`, и это закреплено тестом.
- **`pipe-host.mjs` не устанавливался вовсе** — правка канала жила в бинарнике и не
  доходила до копии, которую запускает DSH.
- **Политика сессии видна острову.** DSH под `never` отклоняет запрос до всех ответчиков:
  карточки не будет при любом здоровье моста. Теперь политика едет вместе с сессией, и
  вид модели пишет «Эта сессия не запрашивает подтверждение» вместо молчания.
- **Резервные копии профиля** ограничены десятью: перезагрузка пишет профиль дважды.

## Честно о непроверенном

Карточку разрешения вживую я по-прежнему **не видел**: для неё нужна сессия с политикой
`ask` и вызов инструмента, требующего разрешения. Сессии в `C:\LocalAI\сoucou` идут с
`never` + полный доступ, а менять настройки DSH пользователь запретил.

Проверено всё до момента «остров получает запрос»: порядок ответчиков (запись в журнале
показывает, что остров первый и впереди было 4 чужих), живой канал, подключение Coucou,
перезапуск моста хостом и самообновление. Когда DSH спросит, в журнале появится
`approval: asked by DSH (tool=…, client=yes)`.
